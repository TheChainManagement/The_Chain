## What was done

1. SYSTEM_DESIGN.md does define the broad Wave 1 architecture shape: Next.js App Router + Server Actions, Supabase Postgres/RLS, Workflow DevKit orchestration, QBO native sync, Python forecasting, and Claude explanations. The design explicitly routes crash-sensitive work through workflows at SYSTEM_DESIGN.md:26 and lists Wave 1 workflows at SYSTEM_DESIGN.md:72-76: `qboInitialSyncWorkflow`, `qboIncrementalSyncWorkflow`, `forecastTenantBatchWorkflow`, `purchaseOrderLifecycleWorkflow`, and `onboardingWorkflow`.

2. The schema covers the main nouns from PROJECT.md and PRD.md at a high level. It has tenants/users/roles (`tenants`, `profiles`, `tenant_members`, `departments`, SYSTEM_DESIGN.md:133-138), locations and stock (`locations`, `products`, `inventory_levels`, `stock_movements`, SYSTEM_DESIGN.md:140-145), procurement (`suppliers`, `product_suppliers`, `purchase_orders`, `purchase_order_lines`, `supplier_performance`, SYSTEM_DESIGN.md:147-152), forecasting (`forecasts`, `forecast_points`, `forecast_evaluations`, `inventory_policy`, SYSTEM_DESIGN.md:154-158), cycle counts (SYSTEM_DESIGN.md:160-162), integrations (`source_connections`, `sync_runs`, SYSTEM_DESIGN.md:164-166), and alerts/insights/audit (`alerts`, `notification_preferences`, `insights`, `audit_log`, SYSTEM_DESIGN.md:168-172).

3. The document correctly separates the numeric forecast from Claude. PRD.md says "LLM as the demand forecaster" is out and Claude is explanation-only (PRD.md:124-125). SYSTEM_DESIGN.md follows that with `statsforecast` as the actual forecaster (SYSTEM_DESIGN.md:200) and `insights` as an explanation table that "never overrides" the numeric model (SYSTEM_DESIGN.md:171).

## What wasn't done

1. Critical: Wave 1 reorder recommendations are not backed by schema. PRD.md requires "Reorder recommendations + approval" with lifecycle "recommend → approve → export / mark-ordered → mark received" (PRD.md:65), and SYSTEM_DESIGN.md exposes `createPurchaseOrderFromRecommendation(recommendationId)` (SYSTEM_DESIGN.md:56). There is no `reorder_recommendations` table, no recommendation status, no recommendation version, no reason fields, and no link from `inventory_policy` to a generated recommendation. This is not runnable as written.

2. Critical: QBO two-way sync conflict resolution is claimed but not modeled. PRD.md requires "Two-way ERP sync with idempotent writes, retry, and conflict resolution" (PRD.md:48) and Wave 1 writes back generated POs (PRD.md:57). SYSTEM_DESIGN.md has `source_connections.encrypted_credentials` and `sync_runs` (SYSTEM_DESIGN.md:165-166), but `purchase_orders` has no `external_po_id`, `external_version`, `last_synced_at`, `sync_status`, or conflict state (SYSTEM_DESIGN.md:150). `sync_runs` has no idempotency key, cursor fields, entity-level external IDs, or per-record failure table. The threat model says "PO export is keyed by `(po_id, version)`" (SYSTEM_DESIGN.md:190), but `purchase_orders` has no `version` column.

3. High: RLS coverage is asserted, not defined, and the schema contradicts "Every row carries `tenant_id uuid not null`" (SYSTEM_DESIGN.md:85). Tenant data tables without `tenant_id` include `purchase_order_lines` (SYSTEM_DESIGN.md:151), `forecast_points` (SYSTEM_DESIGN.md:156), `forecast_evaluations` (SYSTEM_DESIGN.md:157), `cycle_count_lines` (SYSTEM_DESIGN.md:162), and `sync_runs` (SYSTEM_DESIGN.md:166). Those can be protected through parent joins, but SYSTEM_DESIGN.md only gives "representative" policies (SYSTEM_DESIGN.md:174-180), not actual policies. The PRD requires multi-tenant isolation via Supabase RLS from day one (PRD.md:39); this document does not prove it.

4. High: The SourceAdapter contract is missing. PRD.md says Phase 2 must commit the "source-adapter contract" and that CSV, QBO, Rutter, and future natives all sit behind it (PRD.md:49, PRD.md:115). SYSTEM_DESIGN.md names QBO and Rutter but never defines a TypeScript interface, canonical payload shape, external ID mapping contract, idempotency contract, error contract, or required adapter methods. The acceptance test at SYSTEM_DESIGN.md:264 references `RutterSourceAdapter`, `QboSourceAdapter`, and `SourceAdapter`, but none of those contracts exist in the design.

5. High: The greenfield onboarding path is not backed by minimum-field schema or workflow detail. PRD.md requires dual onboarding: "Connect QuickBooks Online + optional CSV history" versus "Start fresh" with "guided minimum-field setup" (PRD.md:56) and repeats that as an acceptance check (PRD.md:140). SYSTEM_DESIGN.md has `onboardingWorkflow(tenantId, path: 'qbo' | 'csv' | 'fresh')` (SYSTEM_DESIGN.md:76), but no minimum required fields, no cold-start policy table, no baseline assumptions, no manual setup object, and no acceptance test for fresh-start SKUs.

6. Medium: Supplier scorecard aggregation is under-modeled. PRD.md requires "Supplier reliability scorecard" from promised-vs-actual timeseries, visible per supplier from the first qualifying PO (PRD.md:66). SYSTEM_DESIGN.md has raw `supplier_performance` rows (SYSTEM_DESIGN.md:152), but no index on `(tenant_id, supplier_id, recorded_at)`, no materialized rollup, no definition of score formula, no treatment for partial receipts across multiple lines, and no query contract for "first qualifying PO."

## What can be done better

1. Add the missing operational indexes before implementation. The current explicit indexes are only `inventory_levels` on `(tenant_id, location_id)` and `(tenant_id, product_id)`, `stock_movements` on `(tenant_id, product_id, occurred_at)`, and `audit_log` on `(tenant_id, entity_type, occurred_at)` (SYSTEM_DESIGN.md:144-145, SYSTEM_DESIGN.md:172). Add at least: `stock_movements(tenant_id, location_id, occurred_at)` for location dashboards; `forecasts(tenant_id, product_id, location_id, computed_at desc)` for latest forecast lookup; `forecast_points(forecast_id, period_date)` is already PK but needs parent lookup coverage through `forecasts`; `forecast_evaluations(forecast_id, evaluated_at desc)`; `purchase_orders(tenant_id, status, expected_delivery_at)` for late PO alerts; `supplier_performance(tenant_id, supplier_id, recorded_at)` for scorecards; `audit_log(tenant_id, actor_user_id, occurred_at)` for user/date audit queries.

2. Make audit and ledger growth a first-class design decision. The design says every state change writes `audit_log` (SYSTEM_DESIGN.md:26) and `stock_movements` is append-only (SYSTEM_DESIGN.md:145), but the only scale mitigation is forecast fan-out (SYSTEM_DESIGN.md:272). Add partitioning or retention strategy for `audit_log` and `stock_movements`, plus archival rules for `before`/`after` JSONB. Without this, Wave 6 ROI queries (PRD.md:79) will either scan unbounded JSONB history or require a later schema refactor.

3. Tighten the Workflow DevKit boundary. The docs define `"use workflow"` as deterministic/sandboxed and `"use step"` as the side-effecting unit with full Node access; steps called outside a workflow lose retry/observability semantics. SYSTEM_DESIGN.md says Python "writes forecast tables" in the architecture diagram (SYSTEM_DESIGN.md:21, SYSTEM_DESIGN.md:248), but later says the Python function returns forecast points to a step (SYSTEM_DESIGN.md:42). Pick one contract: the step should own DB writes so retries and idempotency are controlled in the Workflow event model. If Python writes directly, the design needs DB idempotency keys and duplicate-write handling.

4. Fix the hook/webhook plan. SYSTEM_DESIGN.md defines custom `POST /api/workflows/webhook/[token]` wrapping `resumeWebhook(token, request)` (SYSTEM_DESIGN.md:65). Workflow DevKit docs state `createWebhook()` is automatically addressable at `/.well-known/workflow/v1/webhook/:token`; manual route wrapping is for hooks via `resumeHook()`, not the normal `createWebhook()` path. Also, `purchaseOrderLifecycleWorkflow` waits for a "mark received" hook (SYSTEM_DESIGN.md:75), while the product action `markPurchaseOrderReceived(poId, lines[])` already closes the lifecycle (SYSTEM_DESIGN.md:58). Define this as a Server Action that validates tenant/RBAC, writes receipt state idempotently, and resumes a hook token stored against the PO if a workflow is actually waiting.

5. Replace "representative" RLS with table-specific policies. PRD.md requires role-based access from day one (PRD.md:41). SYSTEM_DESIGN.md says RLS policies use `tenant_id = auth.jwt() ->> 'tenant_id'` and a helper `has_role(role_required)` (SYSTEM_DESIGN.md:177-178), but does not define which roles can write `purchase_orders`, receive POs, edit suppliers, view subscriptions, or read audit history. The Wave 3 acceptance test at SYSTEM_DESIGN.md:262 cannot pass until those policies are explicit.

6. Add a dead-letter and retry persistence model. SYSTEM_DESIGN.md names `RetryableError` and `FatalError` (SYSTEM_DESIGN.md:79) and `sync_runs.error_log` (SYSTEM_DESIGN.md:166), but there is no `dead_letter_events`, `failed_sync_records`, retry count, next retry timestamp, or operator-facing recovery state. QBO sync, webhooks, and PO export need durable failure records, not just workflow-level errors.

## What was missed

1. Critical: The auth model is vulnerable to stale or wrong tenant claims in multi-tenant membership. SYSTEM_DESIGN.md allows many `tenant_members` rows per user (SYSTEM_DESIGN.md:136), then says the JWT carries one `tenant_id` and `role` from an auth hook (SYSTEM_DESIGN.md:175, SYSTEM_DESIGN.md:184). There is no active-tenant table, tenant switch flow, JWT refresh requirement after role changes, or stale-claim invalidation. This is exactly where horizontal privilege escalation and stale authorization bugs happen.

2. Critical: Wave 1 forecast acceptance is not fully supported. PRD.md requires every promoted forecast to beat a seasonal-naive baseline on rolling-origin backtest, with RMSSE and WAPE stored as the auditable record (PRD.md:133-135). SYSTEM_DESIGN.md stores `rmsse`, `wape`, and `beats_baseline` in `forecast_evaluations` (SYSTEM_DESIGN.md:157), but does not store rolling-origin window metadata, training cutoff, test period, baseline forecast values, eligibility threshold, sparse-data/cold-start status, or "promoted" versus rejected forecast state. The acceptance check is therefore aspirational.

3. High: ABC classification is underspecified. PRD.md requires "ABC by value, XYZ from the ADI/CV² classifier" (PRD.md:44) and Wave 1 visibility per SKU (PRD.md:63). SYSTEM_DESIGN.md stores `abc_class`, `xyz_class`, `adi`, and `cv_squared` (SYSTEM_DESIGN.md:143), but has no annual consumption value, revenue/cost basis, classification threshold version, or location-specific classification support. ABC cannot be audited or recomputed consistently from this design alone.

4. High: Alerts are named but not derivable. PRD.md requires in-app alerts for stockout risk, reorder-needed, overstock, and late incoming PO (PRD.md:68). SYSTEM_DESIGN.md has an `alerts` table (SYSTEM_DESIGN.md:169), but no generation workflow, no dedupe key, no entity-specific uniqueness, no reopen/suppress rule, and no index on `(tenant_id, status, severity, created_at)`. Without a dedupe contract, nightly forecast runs can spam duplicate alerts.

5. High: Acceptance tests are not genuinely runnable against the committed schema. SYSTEM_DESIGN.md says the tests are "explicit" (SYSTEM_DESIGN.md:258-259), but several depend on missing contracts: `existing Server Actions accept a location_id parameter` (SYSTEM_DESIGN.md:261) while only `recomputeForecast(productId?, locationId?)` names `locationId` (SYSTEM_DESIGN.md:55); role differentiation on `audit_log`, `purchase_orders`, and `subscriptions` (SYSTEM_DESIGN.md:262) has no table-specific RLS policy; Rutter/Cin7 adapter tests reference undefined `SourceAdapter` contracts (SYSTEM_DESIGN.md:264, SYSTEM_DESIGN.md:266); ROI test assumes `before`/`after` JSONB contains expediting cost and inventory reduction data (SYSTEM_DESIGN.md:265), but no schema or audit trigger contract guarantees those fields.

6. Medium: The design defers a scale problem that PROJECT.md says should be architected now. PROJECT.md says "Architect for the full vision now" and "No future wave requires a schema change or foundational refactor" (PROJECT.md:13-15). SYSTEM_DESIGN.md then says tenants over 50K SKUs "may need a sharded batch strategy" and to "Defer that work until a pilot tenant hits it" (SYSTEM_DESIGN.md:272). That is a direct posture mismatch. The implementation can wait, but the sharding/backpressure contract should not be deferred in Phase 2.
