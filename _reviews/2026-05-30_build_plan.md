## What was done
1. Required source artifacts were read before judgment: `PROJECT.md`, `PRD.md`, `SYSTEM_DESIGN.md`, `DESIGN_DIRECTION.md`, `DESIGN.md`, `FEATURES.md`, `MASTER_PROMPT.md`, and root `PROCESS.md`. This matches the Phase 4 checkpoint scope in `PROCESS.md:165-168`, which says the Codex checkpoint pressure-tests `PRD`, `SYSTEM_DESIGN`, `DESIGN_DIRECTION`, `FEATURES`, and `MASTER_PROMPT` for "missing features (PRD coverage), vague acceptance criteria, weak rules in MASTER_PROMPT, missing edge cases, unaddressed risks."

2. The major Wave 1 PRD feature list is mostly represented in `FEATURES.md`. PRD Wave 1 lists account/auth, onboarding, QBO + CSV sources, product catalog, sales/movement ingestion, suppliers, demand prediction, inventory optimization, ABC/XYZ, Days of Supply + Stockout Risk, reorder workflow, supplier scorecard, dashboard, alerts, AI insights, and audit log writes (`PRD.md:54-70`). `FEATURES.md` has corresponding blocks for account creation (`FEATURES.md:29`), onboarding (`FEATURES.md:63`), CSV import (`FEATURES.md:158`), QBO integration (`FEATURES.md:190`), products/SKUs (`FEATURES.md:98`), suppliers (`FEATURES.md:130`), classification (`FEATURES.md:225`), forecasting (`FEATURES.md:254`), inventory policy (`FEATURES.md:288`), scorecards (`FEATURES.md:318`), reorder lifecycle (`FEATURES.md:347`), AI insights (`FEATURES.md:380`), alerts (`FEATURES.md:410`), audit/retention (`FEATURES.md:440`), and dashboard (`FEATURES.md:470`).

3. The strongest acceptance criteria are the forecasting and PO lifecycle checks because they preserve the PRD's measurable product bar. PRD requires every promoted forecast to beat seasonal-naive on rolling-origin backtest with RMSSE/WAPE and bans MAPE (`PRD.md:133-134`); `FEATURES.md` carries that into the forecast block (`FEATURES.md:272-276`). PRD requires the PO lifecycle to run recommend -> approve -> export/mark-ordered -> receive -> on-hand update (`PRD.md:136`); `FEATURES.md` gives that a concrete block and partial-receipt criteria (`FEATURES.md:347-369`).

4. The design execution rules are unusually concrete and mostly reviewable. `DESIGN_DIRECTION.md` defines the cobalt hierarchy with explicit allowed intents and a "Maximum 4 cobalt intents visible at any viewport" rule (`DESIGN_DIRECTION.md:100-111`), and `MASTER_PROMPT.md` restates the same rule (`MASTER_PROMPT.md:19`). The marketing/app split is also enforceable: `MASTER_PROMPT.md:27` says marketing routes use no bench layout or rails, and the marketing feature acceptance repeats "no rails on marketing pages" (`FEATURES.md:550-555`).

5. Scope discipline is mostly intact on later-wave UI. The PRD defers multi-location, role dashboards, barcode/cycle-count UI, Rutter, ROI dashboard, and distribution ERP natives to later waves (`PRD.md:72-80`). The Wave 1 feature blocks mostly avoid shipping those UIs. The exceptions are data-layer or wiring only: role claims and RLS in account/auth (`FEATURES.md:47-48`), cycle-count schema only in system design (`SYSTEM_DESIGN.md:190-192`), Rutter in the adapter contract (`SYSTEM_DESIGN.md:255-257`), and ROI-readiness via audit log (`FEATURES.md:457-460`).

## What wasn't done
1. Blocker: The wired-for acceptance suite promised by `SYSTEM_DESIGN.md` is not codified in `FEATURES.md`. `SYSTEM_DESIGN.md:448` says "These tests are codified in Phase 4 (FEATURES.md) and run as part of the Wave 1 acceptance suite." The actual feature blocks do not contain explicit acceptance checks for the full list at `SYSTEM_DESIGN.md:439-446`: multi-location UI activation, multi-user role dashboard activation, cycle counts + browser barcode activation, Rutter adapter activation, ROI dashboard audit-readiness, distribution ERP native activation, pricing model swap, and tier-gated retention. Pricing/retention are partially covered in `FEATURES.md:518-522` and `FEATURES.md:457-460`, but the rest are missing as explicit Wave 1 acceptance checks. This is a Phase 5 blocker because PRD says wired-for verification must be demonstrable at Wave 1 ship (`PRD.md:144-146`).

2. Blocker: The CSV path does not clearly implement the same source-adapter contract as QBO, contradicting the PRD. PRD requires QBO and CSV to sit "behind the same source-adapter interface" (`PRD.md:57`). QBO explicitly implements `QboSourceAdapter` conforming to `SourceAdapter` (`FEATURES.md:202`), but CSV is described as parsing, mapping, validating, previewing, and bulk inserting (`FEATURES.md:167-174`) with no `CsvSourceAdapter`, no `pull(kind, cursor, idempotencyKey)`, and no capability flags. This breaks the canonical adapter promise in `SYSTEM_DESIGN.md:212-273`.

3. Blocker: Sales/movement ingestion exists only as implied work, not as a verifiable feature outcome. PRD makes "Sales / movement data ingestion (QBO sync + CSV)" a Wave 1 feature (`PRD.md:59`) and the forecasting feature depends on `stock_movements` as input (`FEATURES.md:258-261`). CSV import offers "sales history" as an import kind (`FEATURES.md:168`), and QBO sync pulls "bills -> sales" (`FEATURES.md:203`), but no acceptance criterion verifies that sales, receipts, adjustments, or bills normalize into `stock_movements`, preserve `occurred_at`, and feed forecasts. A broken ingestion mapper could still pass the current criteria.

4. Blocker: There is no explicit Phase 5 foundation/schema/RLS feature block even though the project philosophy says the schema, RLS policies, adapter contracts, audit log, and durable workflow primitives are day-one scope. `PROJECT.md:12-17` and `PRD.md:113-117` make "architect for the full vision now" a hard principle. `MASTER_PROMPT.md:22` repeats it. `FEATURES.md` starts directly with account creation and feature surfaces; it lacks a dedicated foundational database migration/RLS/adapter-contract acceptance block that proves every table in `SYSTEM_DESIGN.md:157-204` exists, every RLS rule in `SYSTEM_DESIGN.md:291-330` is implemented, and every wired-for schema test passes before feature work begins.

5. The PRD's "single-tenant single-location single-user UI on top of the multi-everything schema" (`PRD.md:55`) has no direct FEATURES block or acceptance criterion. Pieces exist indirectly: the locations table auto-creates "Main" in `SYSTEM_DESIGN.md:165`, the fresh onboarding path creates first location/default Main (`FEATURES.md:77`), and dashboard says "single location" in its why line (`FEATURES.md:470-472`). But there is no acceptance criterion proving the Wave 1 UI suppresses multi-location/multi-user affordances while the data layer still supports them.

6. Subscription/trial/billing and marketing site are legitimate practical needs, but they are not named in the PRD Wave 1 feature list. `FEATURES.md` adds "Subscription, trial, billing wiring" (`FEATURES.md:501`) and "Marketing site" (`FEATURES.md:532`). Account sign-up with 14-day trial is supported by system design (`SYSTEM_DESIGN.md:276-277`) and the marketing site is implied by GTM, but both are scope additions relative to the explicit Wave 1 bullets (`PRD.md:54-70`). Treat this as an MG approval question, not an automatic defect.

## What can be done better
1. Tighten vague acceptance language around "real account" and "appropriately." Onboarding says "Every path can complete end-to-end with a real account" (`FEATURES.md:82`), QBO says "OAuth complete + first sync running within 60 seconds of connect" (`FEATURES.md:209`), and billing says trial expiration "gates app surfaces appropriately" (`FEATURES.md:520`). These are not precise enough for Phase 6 review. Define the fixture/account type, exact terminal states, which routes become read-only, which remain available, and the expected database rows.

2. The audit-log requirement is still too soft where it matters most. `MASTER_PROMPT.md:26` says `before`/`after` JSONB must carry "enough information" for Wave 6 ROI, and `FEATURES.md:458` says "sufficient to compute Wave 6 ROI metrics later." `SYSTEM_DESIGN.md:443` is more concrete: deltas for `inventory_levels`, `purchase_orders`, and `stock_movements` must compute stockout reduction, inventory reduction, expediting cost, and payback. FEATURES should name required fields per entity, or Phase 6 reviewers cannot prove "rich enough."

3. Performance criteria need test harness definitions. Product list under 800ms for 5,000 SKUs (`FEATURES.md:115`), classification under 1.2s (`FEATURES.md:244`), 10,000-row CSV under 30s (`FEATURES.md:177`), forecast batch 5,000 SKUs under 15 minutes (`FEATURES.md:275`), alert tray under 300ms (`FEATURES.md:430`), audit query under 500ms (`FEATURES.md:459`), and dashboard under 1.2s (`FEATURES.md:488`) are measurable, but the build plan does not say warm/cold cache, local/preview/prod, seeded data shape, or percentile target. Without that, passing can be gamed.

4. Several Codex review checklists are too thin for the risk surface. Supplier master data has only two checklist items (`FEATURES.md:150-152`) and does not ask for tenant isolation, supplier/product link authorization, or downstream policy invalidation. Alerts only checks idempotency and dedupe key stability (`FEATURES.md:432-434`) even though `SYSTEM_DESIGN.md:357-367` defines severity rise, auto-close, notification side-effect idempotency, and re-alert behavior. Billing only checks trial expiration and Stripe webhook idempotency (`FEATURES.md:524-526`) but does not check that planner/viewer roles cannot modify subscriptions, despite `SYSTEM_DESIGN.md:300` making subscriptions system-only for insert/update/delete and selectable only by owner/finance.

5. Some "What's memorable" lines are implementable; a few are still soft or risk visual overload. Strong examples: onboarding chain (`FEATURES.md:94`), PO detail full-size chain (`FEATURES.md:376`), and forecast caption with RMSSE lift (`FEATURES.md:284`). Softer examples: dashboard says "This IS the workshop" and lists atmosphere elements (`FEATURES.md:497`) but does not name one required interaction/state transition; sign-up says "the workshop is open by the time the user blinks" (`FEATURES.md:59`), which is aspirational unless paired with a specific transition timing and success state.

6. MASTER_PROMPT's "Ship a visible craft delta with every feature" is intentionally subjective unless tied back to each feature block. `MASTER_PROMPT.md:21` says each feature must ship a distinctive interaction/layout/motion moment beyond token compliance; `MASTER_PROMPT.md:52` says a feature is under-designed if the line is empty. That catches missing lines, not weak lines. Add a review trigger: the memorable element must be visible in the preview, named in the feature acceptance criteria, and testable by screenshot or interaction.

7. The trust hierarchy is enforceable in design review but needs code-level hooks. `MASTER_PROMPT.md:20` and `DESIGN_DIRECTION.md:228-236` clearly separate statistical output, Claude prose, and user action. The enforceability gap is not the rule; it is the lack of component constraints. Add named components or lintable conventions such as `StatNumber`, `ClaudeInsight`, and `ActionButton` so Phase 6 can grep usage instead of relying on taste review.

## What was missed
1. Edge case: long-running PO lifecycle survival is only partly covered. `SYSTEM_DESIGN.md:82` says `purchaseOrderLifecycleWorkflow` waits for mark received and survives long sleeps. The adversarial scenario is a PO waiting six months for receipt. `FEATURES.md:371-374` checks kill/resume and deterministic hook resumption, but not workflow retention/run expiry, hook token durability, or what happens if the tenant's subscription lapses while a PO is still in flight. Add an acceptance case for a months-long pending PO.

2. Security edge case: role abuse around billing and audit export is not covered enough. `SYSTEM_DESIGN.md:300` says `subscriptions` are owner/finance select and system-only mutate; `SYSTEM_DESIGN.md:328` says `audit_log` is selectable by owner/manager/finance only; `SYSTEM_DESIGN.md:73` defines `/api/exports/audit/[period].csv` as tier-gated. FEATURES checks audit-log RLS broadly (`FEATURES.md:463`) but does not explicitly test "planner attempts to modify subscription" or "viewer attempts to export audit log." Those are exactly the kinds of role bugs the future multi-user layer will inherit.

3. Scale edge case: the plan tests 5,000 SKUs and 10,000-row CSV, but the build philosophy says the first persona is 500-5,000 active SKUs (`PRD.md:21`) while architecture is meant to scale upward (`PROJECT.md:29-30`). The requested stress cases, CSV with 50K rows and tenant with 50K SKUs, are not out of Wave 1 if they are used as degradation tests. `SYSTEM_DESIGN.md:350-355` says very-high-SKU tenants "simply have more shards," but `FEATURES.md:275` only accepts 5,000 SKUs in 15 minutes and `FEATURES.md:177` only accepts 10,000 CSV rows. Add non-SLO stress tests that prove graceful queuing/backpressure at 50K, even if the Wave 1 SLO remains 5K.

4. Conflict-resolution edge cases are under-tested. `SYSTEM_DESIGN.md:87-93` defines server-wins for Chain-generated POs, last-write-wins for catalog/vendor edits, separate stock movements for receipt divergence, and `needs_review` for unresolved conflicts. QBO acceptance only checks OAuth, token refresh, 15-minute sync, PO write-back, and disconnect (`FEATURES.md:208-213`). The checklist mentions idempotency and rate limits (`FEATURES.md:215-219`) but does not require tests for each conflict policy branch or the `resolveSyncConflict` owner path.

5. Forecast eligibility is underspecified at the FEATURES level. PRD says "A demand forecast is produced for every eligible SKU. Below threshold, the SKU is on the cold-start ladder" (`PRD.md:133`), and system design has `eligibility_threshold_met` plus `cold_start_state` (`SYSTEM_DESIGN.md:182`). FEATURES says cold-start SKUs show "warming up" and a category benchmark (`FEATURES.md:276`) but never defines the eligibility threshold, cold/warming/warm transitions, or what category benchmark means. This will cause inconsistent forecast behavior across code and review.

6. Wave 1 scope discipline question: the classification feature introduces a drag-zoom quadrant (`FEATURES.md:250`) and the inventory policy feature introduces real-time slider what-ifs (`FEATURES.md:303-314`). Both are in the spirit of Wave 1, but they are heavier UI than the PRD explicitly names. They are not later-wave creep like Rutter or barcode, but MG should explicitly approve them because they can consume Phase 6 time before the core reorder loop is proven.

7. MASTER_PROMPT has two hardcoded-style exceptions embedded in the "Never hardcode" rule set. `MASTER_PROMPT.md:35` bans hardcoded colors, fonts, spacing, shadow, or motion values, but `MASTER_PROMPT.md:45` spells out exact shadow values (`rgba(255,255,255,0.12)` and `0 8px 24px -16px rgba(9,66,181,0.35)`). That is not fatal because the values come from design direction, but it is contradictory unless those shadows are promoted to named CSS variables in the token file before coding starts.
