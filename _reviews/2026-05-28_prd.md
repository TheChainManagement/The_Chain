# Phase 1 PRD — Adversarial Review
Date: 2026-05-28
Unit: Phase 1 PRD
Reviewer: Codex (GPT-5)
Pass type: Lightweight — sanity-check only, not a full architecture or feasibility audit.

## What was done
1. The PRD correctly carries forward the Phase 0 target market and problem. `Problem statement` and `Target users` both match PROJECT.md's framing around "small and mid-sized retailers and distributors" making inventory decisions through "spreadsheets, memory, and gut feel."

2. The PRD defines a coherent v1 feature surface instead of leaving the product at pitch level. `Feature list` names the expected core pieces: `Demand prediction`, `Inventory optimization`, `Automated reordering`, `Inventory health dashboard`, and `AI insights layer`.

3. The PRD explicitly separates v1 from deferred scope. `Out of scope` correctly excludes "Native mobile app", "Supplier sourcing marketplace", "Live POS / ERP integrations", "Multi-location / multi-warehouse", and "Auto-sending purchase orders directly to suppliers without human approval", which is consistent with PROJECT.md `Non-goals`.

## What wasn't done
4. The import path is underspecified for the highest-risk onboarding case. `Flow 1 — Onboarding and data setup` says the existing user "uploads CSV(s)... maps columns; reviews validated import", but does not say what happens when required columns are missing, rows fail validation, duplicate SKUs exist, units conflict, or sales history is partial.

5. The fresh-start path is too thin to build against. `Flow 1 — Onboarding and data setup` says the fresh user "adds initial products and suppliers manually with guided defaults", but does not define the minimum required fields, how defaults are chosen, or what recommendations are allowed before any sales history exists.

6. Alerts are in v1 scope without a decided channel or user flow. `Feature list` includes `Alerts` for "stockout risk, reorder-needed, and overstock", while `Open questions` leaves "Notification channel: email, in-app, or both" unresolved; a developer cannot fully build alert behavior from that.

## What can be done better
7. `Success criteria` calls the capability bar "top-end standard", but that is not measurable. Replace or supplement it with acceptance checks for each capability, such as forecast generated per eligible SKU, reorder point calculated from defined inputs, and purchase order export produced after approval.

8. `Forecast credibility` is currently not a success criterion; it is a placeholder. The line "once real data exists, set a concrete forecast-accuracy target... number TBD in a later phase" means the team cannot verify whether demand prediction is acceptable during v1 build or pilot.

9. `Primary persona` is useful but still broad enough to hide conflicting needs. "Dana" covers owner-operator and inventory manager across "roughly 200 to 2,000 active SKUs", but the PRD does not specify industry, reorder cadence, data maturity, supplier complexity, or whether Dana sells retail, distributes B2B, or does both.

10. `User flows` need terminal states after each major action. `Flow 3 — Reorder workflow` ends with "exports it or marks the items as ordered", but does not define what changes in inventory state, whether expected receipt dates are tracked, or how the user follows up when items arrive.

## What was missed
11. The PRD bakes in a major assumption that CSV/manual entry is enough for v1 users. `Out of scope` says "Live POS / ERP integrations" are excluded and "v1 uses CSV/manual", but `Problem statement` says reorder cycles happen "weekly or daily"; manual ongoing sales entry may be too burdensome for the exact users being targeted. Hypothesis: this could make the product feel like another spreadsheet unless the PRD defines a low-friction recurring import/update loop.

12. The "wired-for" requirement is repeated but not bounded. PROJECT.md `Constraints` says v2 features and future POS/ERP integrations must have "wiring... in place", and PRD `Out of scope` repeats that "architecture must be wired for the deferred items", but Phase 1 never defines what evidence satisfies that without slipping into v2 work.

13. `Automated reordering` is semantically overstated relative to the described behavior. The feature says "when a SKU hits its reorder point, generate a reorder recommendation", and `Out of scope` excludes auto-sending POs; this is recommendation workflow, not true automated reordering. That wording could create scope creep unless renamed or explicitly constrained.

14. The PRD omits failure and trust states for the `AI insights layer`. It says Claude provides "plain-English explanations of forecasts and recommendations", but there is no requirement for what happens when the explanation conflicts with the numeric model, is low-confidence, or cites a reason based on missing/stale data.
